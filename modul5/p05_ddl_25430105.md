## 1. Identitas dan Parameter Personal Proyek

Berdasarkan ketentuan personalisasi data praktikum menggunakan 2 digit terakhir NIM (**NIM: 25430105** $\rightarrow$ `05`):

1. **Perhitungan Parameter Personal $P$:**
   $$P = (\text{2 digit terakhir NIM} \pmod 9) + 1 = (05 \pmod 9) + 1 = 5 + 1 = \mathbf{6}$$
2. **Aturan Batas Maksimal Pembelian ($P + 2$):**
   $$\text{Batas } P + 2 = 6 + 2 = \mathbf{8\text{ item}}$$
3. **Volume Transaksi Harian:**
   $$\text{Volume Transaksi} = 40 + (5 \times P) = 40 + (5 \times 6) = \mathbf{70\text{ transaksi/hari}}$$
4. **Konvensi Standar Penamaan Kolom Kunci (Sesuai Ketentuan Tugas):**
   - **Kunci Primer (*Primary Key*):** Wajib menggunakan format **`id_<nama_tabel>`**  
     Contoh: `id_pelanggan`, `id_admin`, `id_kategori`, `id_produk`, `id_pesanan`, `id_detail_pesanan`.
   - **Kunci Tamu (*Foreign Key*):** Wajib menggunakan format **`id_<nama_tabel_tujuan>`**  
     Contoh: `id_kategori` (merujuk ke `kategori`), `id_admin` (merujuk ke `admin`), `id_pelanggan` (merujuk ke `pelanggan`), `id_pesanan` (merujuk ke `pesanan`), `id_produk` (merujuk ke `produk`).

## 2. Analisis Mendalam Aturan Batas $P+2$ (Modul 2) dan Daya Jangkau DDL

Sesuai aturan bisnis **AB-03** pada dokumen kebutuhan data Modul 2: *"Batas maksimal pembelian produk dalam satu transaksi pesanan adalah 8 item ($P+2 = 6+2$)."*  
Dalam perancangan fisik DDL, aturan ini dianalisis ke dalam dua tingkatan jangkauan integritas struktural:

```
                                ATURAN BATAS P+2 = 8 ITEM
                                            |
         +----------------------------------+----------------------------------+
         |                                                                     |
[Tingkat Satu Baris / Single-Row]                    [Tingkat Banyak Baris / Multi-Row]
- Kuantitas item per rincian (qty_detail)             - Total item kumulatif per pesanan (SUM(qty))
- Evaluasi nilai kolom pada tuple tunggal             - Evaluasi lintas baris (cross-row aggregation)
- SOLUSI DDL: CHECK (qty_detail BETWEEN 1 AND 8)      - DAYA JANGKAU DDL: TIDAK MAMPU DIJAGA CHECK
- Status: Diimplementasikan di Modul 5                - Status: Ditandai untuk Modul 14 (Transaksi)
```

### 2.1 Analisis Ranah Satu Baris (*Single-Row Scope / Intra-Row*)
- **Objek:** Kuantitas pembelian pada satu baris rincian item barang (`detail_pesanan.qty_detail`).
- **Penerapan Teknis:** Setiap baris item yang dipesan harus bernilai minimal 1 dan tidak boleh melampaui batas atas paket pembelian personal $P+2 = 8$.
- **Realisasi DDL:** Dapat diwujudkan secara mandiri dan efektif menggunakan **`CONSTRAINT CHECK`**:
  ```sql
  CONSTRAINT chk_detail_qty CHECK (qty_detail >= 1 AND qty_detail <= 8) -- [AB-03]
  ```
- **Karakteristik Engine:** Mesin MariaDB (versi 10.2.1+) dan MySQL (versi 8.0.16+) mengevaluasi ekspresi CHECK ini saat operasi `INSERT` maupun `UPDATE`. Jika nilai `qty_detail` bernilai di luar rentang $1 \dots 8$, operasi langsung ditolak dengan pesan kesalahan *Check constraint violated*.

### 2.2 Analisis Ranah Banyak Baris / Akumulasi Transaksi (*Multi-Row Scope / Inter-Row*)
- **Objek:**
  1. Total akumulasi kuantitas seluruh item dalam satu transaksi pesanan: $\sum \text{qty\_detail} \le 8$.
  2. Aturan **AB-01**: Setiap faktur pesanan wajib memuat minimal 1 baris item produk (kardinalitas mandatori $1 \dots N$).
- **Analisis Daya Jangkau DDL (Mengapa CHECK Constraint Tidak Mampu Menjaganya?):**
  1. **Batasan Standar ANSI SQL & RDBMS Engine:** Klausa `CONSTRAINT CHECK` pada standar SQL relasional dirancang khusus untuk memvalidasi predikat skalar pada baris yang sedang diproses (*intra-row predicate*). Mesin basis data secara eksplisit **melarang subquery, fungsi agregasi (`SUM()`, `COUNT()`), maupun pemanggilan tabel silang** di dalam definisi CHECK constraint tabel.
  2. **Anomali Urutan Penyisipan (*Insertion Order Paradox*):** Pada skema relasional, tabel kepala (`pesanan`) harus disisipkan terlebih dahulu sebelum baris anak (`detail_pesanan`) dapat dibuat. Pada mikrodetik ketika baris `pesanan` masuk, jumlah baris detailnya masih 0 (melanggar syarat minimal 1 baris). Tabel induk tidak memiliki mekanisme bawaan untuk menahan diri jika baris anak belum ada.
  3. **Penolakan Validasi Multi-Baris Statis:** MariaDB/MySQL tidak dapat menghitung apakah penambahan baris produk ke-3 menyebabkan total belanja melebihi 8 item hanya melalui deklarasi DDL tabel.
- **Tandai untuk Diselesaikan pada Modul 14:**
  - Keterbatasan DDL ini dicatat secara resmi sebagai **utang desain struktural** yang akan ditangani tuntas pada **Modul 14 (Transaksi ACID dan Integritas Prosedural)**.
  - Solusi Modul 14 akan menggunakan:
    1. **Mekanisme Transaksi Atomik:**
       ```sql
       START TRANSACTION;
       -- INSERT INTO pesanan ...
       -- INSERT INTO detail_pesanan ...
       -- Verifikasi agregat via trigger/aplikasi:
       -- IF (total_qty > 8 OR total_item < 1) THEN ROLLBACK; ELSE COMMIT; END IF;
       ```
    2. **Trigger Integritas Bisnis:** `BEFORE INSERT ON detail_pesanan` untuk menghitung `SUM(qty_detail)` yang telah terdaftar pada `id_pesanan` tersebut dan melempar `SIGNAL SQLSTATE '45000'` jika akumulasi melebihi 8 item.

## 3. Matriks Aturan Bisnis (AB) dan Realisasi Constraint DDL

Tabel berikut memetakan seluruh aturan bisnis dari `p02_kebutuhan_data_25430105.md` ke dalam implementasi constraint fisik:

| Kode AB | Bunyi Aturan Bisnis | Tabel Target | Kolom Terlibat | Jenis Constraint DDL | Sintaks Implementasi DDL |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **AB-01** | Setiap pesanan memiliki nomor invoice unik | `pesanan` | `no_invoice` | `UNIQUE`, `NOT NULL` | `CONSTRAINT uk_pesanan_invoice UNIQUE (no_invoice)` |
| **AB-01** | Pesanan minimal memuat 1 item produk | `pesanan`, `detail_pesanan` | Relasi Induk-Anak | *Multi-row integrity* | *Tidak dapat dijaga DDL murni; Ditandai untuk Modul 14 (Transaksi ACID).* |
| **AB-02** | Pembelian hanya oleh pelanggan terdaftar | `pesanan` | `id_pelanggan` | `FOREIGN KEY` | `CONSTRAINT fk_pesanan_pelanggan FOREIGN KEY (id_pelanggan) REFERENCES pelanggan(id_pelanggan) ON UPDATE CASCADE ON DELETE RESTRICT` |
| **AB-03** | Batas pembelian per item $P+2=8$ ($P=6$) | `detail_pesanan` | `qty_detail` | `CHECK` | `CONSTRAINT chk_detail_qty CHECK (qty_detail >= 1 AND qty_detail <= 8)` |
| **AB-03** | Batas total pembelian per pesanan $\le 8$ | `detail_pesanan` | Agregasi baris | *Multi-row aggregate* | *Tidak dapat dijaga CHECK; Ditandai untuk Modul 14 (Trigger / ACID Transaction).* |
| **AB-04** | Harga produk disimpan historis per rincian | `detail_pesanan` | `harga_satuan_detail` | `DECIMAL`, `CHECK` | `CONSTRAINT chk_detail_harga CHECK (harga_satuan_detail >= 0)` |
| **AB-05** | Stok produk tidak boleh bernilai negatif | `produk` | `stok_produk` | `CHECK` | `CONSTRAINT chk_produk_stok CHECK (stok_produk >= 0)` |
| **AB-06** | Email dan No HP pelanggan unik | `pelanggan` | `email_pelanggan`, `no_hp_pelanggan` | `UNIQUE` | `CONSTRAINT uk_pelanggan_email UNIQUE (email_pelanggan)`,<br>`CONSTRAINT uk_pelanggan_no_hp UNIQUE (no_hp_pelanggan)` |
| **AB-07** | Alamat kirim dan ongkir dicatat per order | `pesanan` | `alamat_kirim`, `ongkir` | `TEXT`, `CHECK` | `alamat_kirim TEXT NOT NULL`,<br>`CONSTRAINT chk_pesanan_ongkir CHECK (ongkir >= 0)` |
| **AB-08** | Status pesanan terkontrol | `pesanan` | `status_pesanan` | `ENUM` | `status_pesanan ENUM('Pending','Lunas','Dikirim','Selesai','Batal') DEFAULT 'Pending'` |

## 5. Diagram ERD Fisik Proyek (Physical Data Model)

### 5.1 Diagram ERD Fisik Format Mermaid
Diagram berikut merepresentasikan skema fisik basis data secara presisi, memuat seluruh tipe data kolom fisik, penanda Primary Key (`PK`), Foreign Key (`FK`), Unique Key (`UK`), serta batasan constraint bisnis:

```mermaid
erDiagram
    pelanggan ||--o{ pesanan : "melakukan (1 : 0..N)"
    admin ||--o{ produk : "mengelola (1 : 0..N)"
    kategori ||--o{ produk : "mengklasifikasi (1 : 0..N)"
    pesanan ||--|{ detail_pesanan : "memuat (1 : 1..8)"
    produk ||--o{ detail_pesanan : "dipesan pada (1 : 0..N)"

    pelanggan {
        INT id_pelanggan PK "AUTO_INCREMENT"
        VARCHAR(20) kode_pelanggan UK
        VARCHAR(100) nama_pelanggan
        VARCHAR(100) email_pelanggan UK "AB-06"
        VARCHAR(20) no_hp_pelanggan UK "AB-06"
        TEXT alamat_pelanggan

    }

    admin {

        VARCHAR(20) kode_admin UK

        VARCHAR(50) peran_admin "Default: Admin Produk"
        VARCHAR(100) email_admin UK
    }

    kategori {
        INT id_kategori PK "AUTO_INCREMENT"
        VARCHAR(20) kode_kategori UK
        VARCHAR(100) nama_kategori
    }

    produk {
        INT id_produk PK "AUTO_INCREMENT"
        VARCHAR(20) kode_produk UK
        VARCHAR(150) nama_produk
        DECIMAL(12_2) harga_produk "CHECK >= 0"
        INT stok_produk "CHECK >= 0 (AB-05)"
        INT id_kategori FK "kategori.id_kategori"

        INT id_pesanan PK "AUTO_INCREMENT"

        TEXT alamat_kirim "AB-07"
        DECIMAL(10_2) ongkir "CHECK >= 0 (AB-07)"

        ENUM status_pesanan "Pending,Lunas,Dikirim,Selesai,Batal (AB-08)"
        INT id_pelanggan FK "pelanggan.id_pelanggan (AB-02)"
    }

    detail_pesanan {
        INT id_detail_pesanan PK "AUTO_INCREMENT"
        INT id_pesanan FK "pesanan.id_pesanan"
        INT id_produk FK "produk.id_produk"
        INT qty_detail "CHECK 1..8 (AB-03)"
        DECIMAL(12_2) harga_satuan_detail "CHECK >= 0 (AB-04)"
    }
```

| **Aksi Referensial** | `ON UPDATE CASCADE`, `ON DELETE RESTRICT` (atau `CASCADE` pada detail) | Terdaftar pada metadata relasi InnoDB (`information_schema.KEY_COLUMN_USAGE`) | **Sesuai (100%)** | Penghapusan induk pesanan akan menghapus rinciannya (`CASCADE`), sedangkan master produk/pelanggan dilindungi dari penghapusan jika masih memiliki transaksi (`RESTRICT`). |
| **Kunci Unik (UK)** | `kode_pelanggan`, `email`, `no_hp`, `no_invoice`, dll. | Terbentuk index unik berjenis `UNIQUE` (*silver key icon*) | **Sesuai (100%)** | Mencegah anomali duplikasi identitas pelanggan dan nomor invoice transaksi. |
| **Batasan CHECK** | `stok_produk >= 0`, `qty_detail BETWEEN 1 AND 8`, dll. | Tersimpan pada metadata tabel (`TABLE_CONSTRAINTS`) | **Sesuai (100%)** | Engine MariaDB 10.2+/MySQL 8.0+ menegakkan validasi CHECK saat operasi DML dijalankan. |

### 6.3 Analisis Perbedaan Representasi Visual Designer vs ERD
1. **Notasi Kardinalitas:** ERD konseptual/fisik menggunakan notasi Crow's Foot yang secara eksplisit membedakan kardinalitas mandatori (`1` atau `1..N`) dan opsional (`0..N`). Pada antarmuka Designer phpMyAdmin, garis relasi hanya menunjukkan keterhubungan titik ke titik (*point-to-point*) antara kolom PK dan FK tanpa memvisualisasikan simbol cabang Crow's Foot.
2. **Keterbacaan Constraint Kompleks:** Aturan bisnis CHECK constraint (seperti batas kuantitas $1 \dots 8$ pada `qty_detail`) tidak ditampilkan sebagai teks di kanvas Designer visual, melainkan tersimpan pada level definisi DDL dan tab *Structure*.

## 7. Skrip DDL Lengkap yang Idempoten

Skrip lengkap di bawah ini dapat dijalankan berulang kali (*re-executable*) dari kondisi basis data kosong tanpa menimbulkan galat tabrakan objek (*object collision*):

```sql
-- =============================================================================
-- PRAKTIKUM BASIS DATA - PERTEMUAN 05: DATA DEFINITION LANGUAGE (DDL)
-- =============================================================================
-- Nama       : Syifa
-- NIM        : 25430105
-- Proyek     : Toko Daring Cendekia SA (Sistem E-Commerce)
-- Parameter P: P = (05 MOD 9) + 1 = 6 -> Batas P+2 = 8 item
-- File       : p05_ddl_25430105.sql
-- =============================================================================

DROP DATABASE IF EXISTS toko_daring_25430105;
CREATE DATABASE toko_daring_25430105
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;

USE toko_daring_25430105;

SET FOREIGN_KEY_CHECKS = 0;
DROP TABLE IF EXISTS detail_pesanan;
DROP TABLE IF EXISTS pesanan;
DROP TABLE IF EXISTS produk;
DROP TABLE IF EXISTS kategori;
DROP TABLE IF EXISTS admin;
DROP TABLE IF EXISTS pelanggan;
SET FOREIGN_KEY_CHECKS = 1;

-- 1. TABEL: pelanggan
CREATE TABLE pelanggan (
    id_pelanggan INT AUTO_INCREMENT,
    kode_pelanggan VARCHAR(20) NOT NULL,
    nama_pelanggan VARCHAR(100) NOT NULL,
    email_pelanggan VARCHAR(100) NOT NULL,
    no_hp_pelanggan VARCHAR(20) NOT NULL,
    alamat_pelanggan TEXT NOT NULL,
    tgl_daftar DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT pk_pelanggan PRIMARY KEY (id_pelanggan),
    CONSTRAINT uk_pelanggan_kode UNIQUE (kode_pelanggan),
    CONSTRAINT uk_pelanggan_email UNIQUE (email_pelanggan),     -- [AB-06]
    CONSTRAINT uk_pelanggan_no_hp UNIQUE (no_hp_pelanggan)      -- [AB-06]
) ENGINE = InnoDB;

-- 2. TABEL: admin
CREATE TABLE admin (
    id_admin INT AUTO_INCREMENT,
    kode_admin VARCHAR(20) NOT NULL,
    nama_admin VARCHAR(100) NOT NULL,
    peran_admin VARCHAR(50) NOT NULL DEFAULT 'Admin Produk',
    email_admin VARCHAR(100) NOT NULL,

    CONSTRAINT pk_admin PRIMARY KEY (id_admin),
    CONSTRAINT uk_admin_kode UNIQUE (kode_admin),
    CONSTRAINT uk_admin_email UNIQUE (email_admin)
) ENGINE = InnoDB;

-- 3. TABEL: kategori
CREATE TABLE kategori (
    id_kategori INT AUTO_INCREMENT,
    kode_kategori VARCHAR(20) NOT NULL,
    nama_kategori VARCHAR(100) NOT NULL,

    CONSTRAINT pk_kategori PRIMARY KEY (id_kategori),
    CONSTRAINT uk_kategori_kode UNIQUE (kode_kategori)
) ENGINE = InnoDB;

-- 4. TABEL: produk
CREATE TABLE produk (
    id_produk INT AUTO_INCREMENT,
    kode_produk VARCHAR(20) NOT NULL,
    nama_produk VARCHAR(150) NOT NULL,
    harga_produk DECIMAL(12, 2) NOT NULL,
    stok_produk INT NOT NULL DEFAULT 0,
    id_kategori INT NOT NULL,
    id_admin INT NOT NULL,

    CONSTRAINT pk_produk PRIMARY KEY (id_produk),
    CONSTRAINT fk_produk_kategori FOREIGN KEY (id_kategori)
        REFERENCES kategori (id_kategori)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT fk_produk_admin FOREIGN KEY (id_admin)
        REFERENCES admin (id_admin)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT uk_produk_kode UNIQUE (kode_produk),
    CONSTRAINT chk_produk_stok CHECK (stok_produk >= 0),         -- [AB-05]
    CONSTRAINT chk_produk_harga CHECK (harga_produk >= 0)
) ENGINE = InnoDB;

-- 5. TABEL: pesanan
CREATE TABLE pesanan (
    id_pesanan INT AUTO_INCREMENT,
    no_invoice VARCHAR(30) NOT NULL,
    tgl_pesanan DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    alamat_kirim TEXT NOT NULL,
    ongkir DECIMAL(10, 2) NOT NULL DEFAULT 0.00,
    total_bayar DECIMAL(12, 2) NOT NULL DEFAULT 0.00,
    status_pesanan ENUM('Pending', 'Lunas', 'Dikirim', 'Selesai', 'Batal') NOT NULL DEFAULT 'Pending',
    id_pelanggan INT NOT NULL,

    CONSTRAINT pk_pesanan PRIMARY KEY (id_pesanan),
    CONSTRAINT fk_pesanan_pelanggan FOREIGN KEY (id_pelanggan)
        REFERENCES pelanggan (id_pelanggan)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT uk_pesanan_invoice UNIQUE (no_invoice),           -- [AB-01]
    CONSTRAINT chk_pesanan_ongkir CHECK (ongkir >= 0),          -- [AB-07]
    CONSTRAINT chk_pesanan_total CHECK (total_bayar >= 0)
) ENGINE = InnoDB;

-- 6. TABEL: detail_pesanan
CREATE TABLE detail_pesanan (
    id_detail_pesanan INT AUTO_INCREMENT,
    id_pesanan INT NOT NULL,
    id_produk INT NOT NULL,
    qty_detail INT NOT NULL,
    harga_satuan_detail DECIMAL(12, 2) NOT NULL,

    CONSTRAINT pk_detail_pesanan PRIMARY KEY (id_detail_pesanan),
    CONSTRAINT fk_detail_pesanan_pesanan FOREIGN KEY (id_pesanan)
        REFERENCES pesanan (id_pesanan)
        ON UPDATE CASCADE
        ON DELETE CASCADE,
    CONSTRAINT fk_detail_pesanan_produk FOREIGN KEY (id_produk)
        REFERENCES produk (id_produk)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT uk_detail_pesanan_item UNIQUE (id_pesanan, id_produk),
    -- Batas kuantitas single-row P+2 = 8
    CONSTRAINT chk_detail_qty CHECK (qty_detail >= 1 AND qty_detail <= 8), -- [AB-03]
    CONSTRAINT chk_detail_harga CHECK (harga_satuan_detail >= 0)          -- [AB-04]
) ENGINE = InnoDB;
```

## 8. Pembahasan dan Kendala

### 8.1 Pembahasan
1. **Penerapan Standar Penamaan Kolom Kunci:**  
   Pemberlakuan aturan seragam di mana Kunci Primer wajib bernama `id_<nama_tabel>` dan Kunci Tamu wajib bernama `id_<nama_tabel_tujuan>` menghasilkan skema yang sangat konsisten dan intuitif (*self-explanatory*). Setiap pengembang maupun *query optimizer* dapat langsung mengetahui asal dan tujuan relasi antar tabel tanpa ambiguitas nama kolom.
2. **Kesesuaian Tipe Data terhadap Kebutuhan Nyata:**  
   Penggunaan tipe data `DECIMAL` pada kolom finansial (`harga_produk`, `ongkir`, `total_bayar`, `harga_satuan_detail`) menjamin presisi matematis dan mencegah potensi selisih pembulatan sen. Di sisi lain, penggunaan tipe `VARCHAR` dan `TEXT` dialokasikan secara proporsional sesuai kamus data tanpa memboroskan ruang blok data disk.

### 8.2 Kendala dan Pemecahan
- **Kendala 1 (Penegakan Aturan Batas Transaksi Multi-Baris):**  
  Mencoba menuliskan `CHECK ((SELECT SUM(qty_detail) FROM detail_pesanan WHERE id_pesanan = ...) <= 8)` menghasilkan galat sintaks pada MariaDB karena constraint CHECK menolak subquery.  
  *Pemecahan:* Memecah aturan menjadi dua ranah: ranah baris tunggal (`qty_detail BETWEEN 1 AND 8`) dijaga oleh CHECK DDL pada Modul 5 ini, sedangkan ranah akumulasi multi-baris ditandai secara formal untuk diselesaikan pada Modul 14 menggunakan kontrol Transaksi ACID dan Database Trigger.
- **Kendala 2 (Idempotensi Eksekusi Skrip DDL):**  
  Saat skrip dijalankan ulang berkali-kali pada lingkungan pengembangan, urutan `DROP TABLE` sering gagal karena terhalang integritas Foreign Key constraint.  
  *Pemecahan:* Menambahkan perintah pembungkus `SET FOREIGN_KEY_CHECKS = 0;` sebelum penghapusan tabel dan mengembalikannya ke `1` setelah pembersihan selesai, serta menyertakan `DROP DATABASE IF EXISTS` agar skrip 100% idempoten dan dapat dieksekusi ulang dari basis data kosong.
